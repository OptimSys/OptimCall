Overview

The Event Notification Service delivers real-time notifications about call and SMS activity to external applications such as CRM systems or helpdesks.

For calls, it reports every relevant change in the state of a call throughout its lifecycle – from the moment a call starts, through the ringing and connection of individual parties, to the moment the call ends and its recording becomes available.

For SMS messages, it reports every change in the state of a received or sent SMS – from the moment an inbound SMS is received or an outbound SMS is queued for sending, through its handover to an SMS gateway, to the moment its sending or delivery is confirmed, or it fails.

This specification documents the event payloads the service sends. Events fall into three groups:

  • Call events describe the call as a whole.
  • Call leg events describe an individual call leg – the connection between OptimCall and a single endpoint (a caller, a called party, a transfer target, or a participant monitoring the call). Each leg event also mirrors the call-level information available at the moment it occurs, so it reflects the state of the call as a whole in addition to the leg's own progress.
  • SMS events describe the progress of an individual SMS message – one received by OptimCall, or one sent by OptimCall through an SMS gateway.

Event payload structure

Within each group, events are cumulative: every event includes all the information of the previous event in its sequence, plus new information specific to that stage. A later event is therefore always a superset of the earlier ones – no attributes present before are ever removed as the call progresses.

The aim is to let integrators treat event handling as stateless wherever possible: a consumer that only needs the final state of a sequence can therefore rely on the last (most detailed) event alone, without tracking or merging the earlier ones.

The one exception is tags: unlike other call details, tags can be added or removed while the call is in progress, so this list can shrink as well as grow from one event to the next.

All durations are measured up to the moment the event occurred. A duration of a call phase reported in an earlier event may therefore be partial and will grow in later events – for example, the total duration or the ringing duration.

Call events

Event What it represents What's included
callStarted A new call has begun Common metadata + basic details about the call as it starts (e.g. who is calling, what number is being called) + the call durations (all 0)
callConnected The call has been answered Everything from callStarted, plus details specific to the moment the conversation starts (e.g. who answered)
callDisconnected The call has ended Everything from the previous event, plus details about how and when the call ended
callRecordingReady A recording of the call is available Everything from callDisconnected, plus details needed to access the recording

callConnected is sent only if the call is answered. If no one answers, it is skipped and the sequence goes straight from callStarted to callDisconnected.

Call leg events

A leg event carries every call-level attribute already available at the moment it occurs and then adds its own leg-specific progression.

Event What it represents What's included
legRinging The leg starts ringing Basic call details + basic leg details + the leg durations (all 0)
legConnected The leg has answered Everything from legRinging, plus details about the answering party
legDisconnected The leg has ended Everything from the previous event, plus which party ended the leg

legConnected is sent only if the leg is answered. A leg that rings but is never answered goes straight from legRinging to legDisconnected.

SMS events

An SMS passes through a sequence of states, and each state is reported by its own event.

Event What it represents SMS direction
smsQueued The SMS is waiting in the OptimCall queue for delivery to the SMS gateway outbound
smsSubmitted The SMS was delivered to the SMS gateway outbound
smsDeferred The SMS is waiting in the SMS gateway's queue for delivery to the recipient outbound
smsSent The SMS gateway confirmed that the SMS was sent; this does not guarantee delivery to the recipient outbound
smsDelivered The SMS gateway received a delivery confirmation outbound
smsReceived The SMS was successfully received by OptimCall inbound
smsFailed An error occurred while the SMS was being sent or received outbound or inbound

An outbound SMS progresses through smsQueued, smsSubmitted, smsDeferred, smsSent and smsDelivered, in this order. Not every event is sent for every SMS:

  • smsDeferred is sent only if the SMS waits in the SMS gateway's queue before it is sent.
  • smsDelivered is sent only if the SMS gateway provides delivery reports and the recipient supports delivery confirmation. Otherwise, smsSent is the last event of the SMS.
  • If an error occurs, the sequence ends with smsFailed instead of progressing further.

An inbound SMS produces a single event: smsReceived, or smsFailed if an error occurred during reception.

Every SMS event carries the complete details of the SMS. The state of the SMS is the only thing that changes as it progresses, and it is given by the name of the event, so the latest event alone is always sufficient. Because failed webhook requests are retried, events of the same SMS may arrive out of order – use eventTime to determine which event is the latest.

Event delivery

The service can deliver the same events in one of two ways, selected by the event delivery mode in the service configuration:

  • Webhook mode – OptimCall sends the events to a predefined HTTPS endpoint provided by the external application, as HTTP POST requests with a JSON body. The endpoint must be publicly accessible and return a 2xx status code to confirm that it received the request. Any other status code is treated as a failure.

    The maximum number of retries and the retry interval for failed requests can be configured (see Delivery retries below).

    An optional security token can be configured. OptimCall then sends it with every request, so that the endpoint can verify that the request really originates from OptimCall (see Authentication below).

  • WebSocket mode – the external application establishes a persistent connection to OptimCall using the WebSocket protocol and receives the events over that connection.

    An optional security token can be configured. Clients must then authenticate with it before they can receive the events (see Authentication below).

Both modes deliver identical event payloads; they differ only in how the connection between OptimCall and the external application is established and maintained. In webhook mode, OptimCall initiates the communication; in WebSocket mode, the external application does.

Which events are delivered is configured using filters (see Event filtering below).

Authentication

An optional security token can be configured for the service. The party that initiates the communication presents the token, and the other party uses it to verify the sender's identity:

  • Webhook mode – if a security token is configured, OptimCall includes it in the X-OptimCall-Key header of every request. The receiving endpoint should use it to verify that the request originates from OptimCall.

  • WebSocket mode – if a security token is configured, the client must connect with the Authorization: Bearer <token> header. If this is not possible (e.g. web browser limitations), the client can alternatively authenticate by sending the

        {
        "name":"authenticate",
        "token":"abc",
        "correlationId": "a1b2c3d4"
    }

    message.

    Regardless of the way the client authenticates, the server sends back the following response:

        {
        "name":"authenticateResult",
        "status":"success",
        "correlationId": "a1b2c3d4"
    }

    In case of an error, the status will be "error".

Delivery retries

If a webhook request fails, OptimCall retries it up to a configurable maximum number of retries, waiting a configurable retry interval (in seconds) between attempts.

Event filtering

Delivery can be narrowed with one or more filters, configured in the service's user interface. An event is delivered if it matches any of the configured filters (filters are combined with OR), and it is delivered only once, even when it matches several filters.

A filter consists of two independent parts: the call part is applied to calls, and the SMS part is applied to SMS messages. Each part works in two steps: it first restricts for which calls (or SMS messages) events are emitted, and then selects which events are delivered for those that passed.

Call part

The call part first restricts for which calls events are emitted:

  • Call type – external inbound, external outbound, and/or internal calls. A call passes if it is of any of the selected types (every call is of only one type) and satisfies the narrowing specified for that type:

    • external inbound calls – all calls, or only calls to the selected public numbers;
    • external outbound calls – all calls, or only calls that use the selected outgoing numbers and/or are dialed from the selected extensions;
    • internal calls – all calls, or only calls made from the selected originating extensions and/or to the selected destination extensions.

    When both criteria of a call type are specified, both must be satisfied. Any number can be specified as the dialing or originating extension, so that calls started via click-to-call from a mobile phone can be matched as well.

For the calls that passed, the call part then selects which events are delivered. All other events of these calls are filtered out:

  • Call events – any subset of the call events listed above.
  • Call leg events – any subset of the call leg events listed above, optionally restricted further:
    • Leg type – caller, callee, transferee, and/or monitoring. Only events of legs of the selected types are delivered.
    • Destination numbers of callee legs – all legs, or only legs to the selected destination numbers. These are typically extensions, but any number can be specified, for example the mobile number of a user. The criterion applies to external inbound and internal calls and is ignored for external outbound calls.

SMS part

The SMS part first restricts for which SMS messages events are emitted:

  • SMS direction – inbound and/or outbound SMS (see the smsDirection attribute).
  • SMS gateway – only SMS received or sent through the selected SMS gateways (see the smsGatewayId and smsGatewayName attributes).

For the SMS messages that passed, the SMS part then selects which SMS events are delivered – any subset of the SMS events listed above.

totalLength
integer

Total call duration, in seconds, measured up to the moment of this event. It is a running total that grows as the call progresses. It is final only once the call ends (callDisconnected / callRecordingReady).

Note that the duration of the Setup phase is excluded, as are post-call interactions within the Conversation phase – both are considered outside the standard call duration. Therefore, the total call duration is not a simple sum of the call phase durations.

The attribute is present in every event, with a value of 0 in callStarted, where no time has yet been counted.

setupLength
integer

Duration of the Setup phase, in seconds, measured up to the moment of this event. The Setup phase applies only to click-to-call calls: it is the time OptimCall spends ringing the caller’s own devices until the caller answers or the attempt times out.

Because OptimCall may ring several caller’s devices with delays between them, the value can be partial in an earlier event and grow in a later one while the phase is still in progress.

The attribute is present in every event, with a value of 0 for calls not initiated via click-to-call and in callStarted, which precedes the Setup phase.

welcomeLength
integer

Duration of the Welcome phase, in seconds. The Welcome phase occurs only in external inbound and internal calls: it is the time spent on initial audio playback and IVR interaction with the caller, and other actions before any attempt to connect the caller with recipients begins.

The attribute is present in every event. Because no event is ever delivered while the Welcome phase is in progress, the value is never a partial measurement: in callStarted it is still 0, as that event precedes the Welcome phase, and in every later event it is the final Welcome phase duration – 0 for external outbound calls and for calls that had no Welcome phase.

ringingLength
integer

Duration of the Ringing phase, in seconds, measured up to the moment of this event. It is the time from the start of call routing to recipients until the call is answered or disconnected.

While the call is in the ringing phase, multiple events can occur – for example, several legRinging events as different legs start ringing. Because of this, the value reported in an earlier event within this phase may be partial and can increase in a later event. It becomes final once the call connects or is disconnected.

The attribute is present in every event, with a value of 0 for calls that had no Ringing phase and in callStarted, which precedes it.

conversationLength
integer

Duration of the Conversation phase, in seconds, measured up to the moment of this event. It covers the time since the call was answered, including periods when the caller is placed on hold or transferred, as well as possible post-call interactions.

Further events can occur while the call is still in conversation – for example, a transfer produces new leg events. In those events the value is partial and can grow in a later event. It is final only in the call-end events, callDisconnected and callRecordingReady.

The attribute is present in every event, with a value of 0 in callStarted and callConnected and for calls that are never answered.

callOutcome
string
Enum: "welcome" "ringing" "conversation" "setupFailed" "voicemail" "blocked" "notRouted" "failed"

Final outcome of the call, indicating how it ended. Possible values:

  • welcome – The call ended during the welcome phase. It is the time spent on initial audio playback and IVR interaction with the caller, and other actions before any attempt to connect the caller with recipients begins. Occurs only for external inbound and internal calls.
  • ringing – The call ended during the ringing phase. It is the time from the start of call routing to recipients until the call is answered or disconnected. It includes announcements played between and after routing attempts.
  • conversation – A recipient answered the call. This outcome also covers calls that ended while on hold, during a transfer, or during a post-call interaction, as these follow the call being answered.
  • setupFailed – During the click-to-call setup phase, either the caller rejected the call or the dial attempt to the caller’s devices timed out.
  • voicemail – The call was routed to voicemail. Occurs only for external inbound and internal calls.
  • blocked – A rule blocked the call before it could reach a recipient. It applies when
    • the caller’s number is on the blocklist of the called number – The caller hears ringing, but the call does not progress.
    • the called number is a public line with no assigned routing scenario.
    • the destination of the outbound call is blocked by the outgoing number rules.
    • the destination of the outbound call is on the blocklist of the trunk.
  • notRouted – The call could not be routed out of the system. The route needed to place it could not be determined, or does not have sufficient capacity. Occurs for external outbound calls when
    • no outgoing number could be determined for the call.
    • no trunk with sufficient capacity could be selected for the call.
  • failed – The call failed due to an error.
disconnectedBy
string
Enum: "caller" "callee" "system"

Indicates which party ended the call:

  • caller – the initiating participant ended the call.
  • callee – the receiving participant ended the call.
  • system – OptimCall ended the call, either automatically, through a user interface action or via an API request from a third-party application.

The value is the same in all events for the SMS. The time at which the SMS reached the state reported by a particular event is given by eventTime.

senderNumber
string

Phone number of the sender. If it is a valid phone number, it is in E.164 format. If the SMS has a text sender instead of a phone number, the sender text is given here.

For an outbound SMS sent through a gateway SIM card that has no phone number configured, the value is SIM N, where N is the number of the SIM card slot.

senderName
string

Name of the contact associated with the sender’s phone number. If several contacts share the same number, the first one is used. If the SMS has a text sender instead of a phone number, the sender text is given here.

This attribute is present only when a contact name is known for the sender’s number or when the SMS has a text sender.

recipientNumber
string

Phone number of the recipient. If it is a valid phone number, it is in E.164 format.

For an inbound SMS received through a gateway SIM card that has no phone number configured, the value is SIM N, where N is the number of the SIM card slot.

recipientName

This attribute is present only when a contact name is known for the recipient’s number.

smsGatewayId
string

Unique identifier of the SMS gateway through which the SMS was received or is being sent.

Unlike the name, which users can change, the identifier is a technical value that stays the same. Use it, not the name, to refer to the gateway programmatically.

smsGatewayName
string

Name of the SMS gateway through which the SMS was received or is being sent, as defined in the gateway’s service settings.

The name is meant for display in user interfaces. As users can change it, use smsGatewayId to identify the gateway.
